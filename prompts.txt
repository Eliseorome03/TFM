PROMPT FASE 1: Motor Simbólico Drools (Java / Spring Boot)


Actúa como un Ingeniero de Software Senior especialista en Java, Spring Boot y Drools Rule Engine (KIE).
Tu objetivo es implementar de forma completa y funcional el microservicio `drools-app` según las especificaciones del archivo SYSTEM_SPEC.md.

Requisitos del microservicio:
1. Framework: Spring Boot 3.x (o 2.7.x compatible con drools-core y drools-compiler 7.x/8.x).
2. Puerto de escucha: 8080.
3. Arquitectura interna:
   - controller/RuleController.java: Expone POST /evaluar. Recibe SolicitudEvaluacion y devuelve ResultadoEvaluacion.
   - model/: Clases POJO con Getters, Setters y constructores:
     * DatosUsuario.java (cantidadSolicitada, plazoMeses, proposito, regimenVivienda, gastoAlquiler, deudaDeclarada, dudaCatchAll).
     * DatosCore.java (clienteId, dni, edad, ingresosNetosMensuales, antiguedadMeses, deudaInternaBanco, esAvalistaSolidario, empresaAvaladaCif).
     * DatosBde.java (consultado, tieneImpagosActivos, importeMorosidadAsnef, deudaCirbe, empresaAvaladaConcurso).
     * CalculosDerivados.java (cuotaEstimada, ratioEndeudamiento, remanenteSubsistencia, edadAlVencimiento).
     * SolicitudEvaluacion.java (contiene las 4 estructuras anteriores).
     * ResultadoEvaluacion.java (estado, reglasDisparadas [List<String>], accionRequerida, datoFaltante, calculosDerivados, articuloNormativo, textoLegal).
   - service/DroolsService.java:
     * Crea e inicializa una KieSession stateless por cada llamada.
     * Calcula o permite derivar cuotaEstimada, ratioEndeudamiento, remanenteSubsistencia y edadAlVencimiento antes o durante el disparo de reglas.
     * Inserta los objetos en la sesión, ejecuta fireAllRules() y recopila los resultados en ResultadoEvaluacion.
   - config/DroolsConfig.java: Configuración de KieServices, KieContainer y KieFileSystem.
   - resources/META-INF/kmodule.xml: Configuración del kmodule estándar de Drools.
   - resources/rules/prestamos.drl: Archivo DRL que implemente con rigor y sin inventar las 10 REGLAS declaradas en SYSTEM_SPEC.md respetando su salience y condiciones lógicas.

Reglas DRL a implementar:

Entrega el código íntegro de:

PROMPT FASE 2: Backend Orquestador (Python / FastAPI)


Actúa como un Desarrollador Backend Senior especialista en Python, FastAPI, SQLAlchemy y arquitecturas de integración de LLMs.
Tu objetivo es implementar el servicio `backend` según el archivo SYSTEM_SPEC.md, encargado de la orquestación, conexión con Mistral, gestión de base de datos MariaDB y registro de auditoría.

Requisitos técnicos del backend:
1. Framework: FastAPI con Uvicorn en el puerto 8000.
2. ORM: SQLAlchemy conectado a MariaDB (pymysql).
3. Cliente LLM: Uso de la librería oficial de Mistral (mistralai) o LangChain Mistral para structured output garantizado mediante Pydantic.
4. Organización modular de carpetas según SYSTEM_SPEC.md:
   - config.py: Variables de entorno (DATABASE_URL, DROOLS_URL, MISTRAL_API_KEY).
   - database.py: Base, engine y get_db session.
   - models/:
     * cliente.py: Mapeo de la tabla 'clientes' (cliente_id, dni, nombre, edad, ingresos_netos_mensuales, antiguedad_meses, deuda_interna_banco, es_avalista_solidario, empresa_avalada_cif).
     * traza.py: Mapeo de 'trazas_auditoria' (id, session_id, turn_id, step_order, component, action_type, step_input, step_output, information_state, created_at).
   - schemas/:
     * nlu.py: Esquema Pydantic EsquemaNLU para la salida forzada de Mistral.
     * drools.py: Modelos de intercambio con la API de Drools.
     * state.py: Modelo del Information State canónico.
     * chat.py: Request (mensaje, cliente_id, session_id) y Response (respuesta, session_id, turn_id).
   - clients/:
     * mistral_client.py:
       - extraer_nlu(mensaje: str) -> EsquemaNLU: Prompt del sistema para estructuración en JSON.
       - generar_nlg(state: dict, mensaje_usuario: str) -> str: Prompt estricto de solo lectura que usa el estado consolidado de Drools y su justificación normativa para generar el mensaje natural al usuario.
     * drools_client.py:
       - evaluar_reglas(payload: dict) -> dict: Llamada HTTP POST a DROOLS_URL con manejo de errores y timeout.
   - services/:
     * audit_tracker.py: Clase AuditTracker que recibe session_id, turn_id y db session. Método record_step(component, action_type, step_input, step_output, state_update) que clona el estado y persiste una fila atómica en trazas_auditoria.
     * bde_mock_service.py: Devuelve datos CIRBE/ASNEF simulados basados en el DNI.
     * orchestrator.py: Contiene procesar_turno_conversacional(mensaje, cliente_id, session_id, db). Ejecuta los 7 pasos secuenciales definidos en SYSTEM_SPEC.md y registra cada micro-acción en el AuditTracker.
   - routers/:
     * chat_router.py: Endpoint POST /api/chat.
     * clientes_router.py: Endpoint GET /api/clientes (para alimentar la interfaz).
     * bde_mock_router.py: Endpoint GET /api/mock/bde/{dni}.
   - main.py: Inclusión de routers, CORS y montaje de estáticos en /static.
   - requirements.txt: Lista de dependencias necesarias.
   - Dockerfile: Dockerfile funcional para compilar con pip.
5. Paradigma de Programación Estricto (POO):
   - Todo el código debe estar estructurado mediante Programación Orientada a Objetos (clases y métodos).
   - Prohibido dejar funciones sueltas procedurales en clients/ y services/.
   - Implementa clases de servicio bien definidas:
     * class MistralClient en app/clients/mistral_client.py.
     * class DroolsClient en app/clients/drools_client.py.
     * class BdeMockService en app/services/bde_mock_service.py.
     * class PipelineOrchestrator en app/services/orchestrator.py (inyectando dependencias en el __init__).
   - Los routers de FastAPI deben limitarse a instanciar o recibir mediante inyección de dependencias (Depends) estas clases de servicio.

Entrega el código íntegro, sin elisiones ni comentarios TODO, de cada uno de los archivos indicados, junto a requirements.txt y el Dockerfile.
