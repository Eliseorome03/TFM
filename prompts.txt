PROMPT FASE 1: Motor Simbólico Drools (Java / Spring Boot)


Actúa como un Ingeniero de Software Senior especialista en Java, Spring Boot y el motor de reglas Drools (KIE).

Tu objetivo es implementar de forma completa, robusta y funcional el microservicio `drools-app` basándote estrictamente en el archivo `SYSTEM_SPEC.md`. Este microservicio actúa como el motor de decisiones simbólico y auditable dentro de una arquitectura neurosimbólica Kautz Nivel 1-2.

REQUISITOS CRÍTICOS DE ARQUITECTURA Y TIPADO:
1. Convenciones Java y Null-Safety: Es OBLIGATORIO usar Clases Wrapper (`Double`, `Integer`, `Boolean`) en todos los atributos de los POJOs (nunca tipos primitivos) para permitir la evaluación de nulos (`== null`). Genera constructores, getters y setters manualmente sin omitir ninguno.
2. Condición de Guarda Anticolisión (DRL): Para evitar que reglas de menor prioridad sobreescriban decisiones previas, TODAS las reglas deben incluir como condición en el `when`:
   `$res : ResultadoEvaluacion(estado == "EN_PROCESO")`
   Si una regla previa cambió el estado (a DENEGADO, REQUIERE_DATOS, etc.), ninguna regla posterior debe dispararse.

Estructura de archivos y requerimientos:

1. `pom.xml` y `Dockerfile`:
   - Spring Boot 3.x con Java 17 (o 2.7.x compatible con drools 7.x/8.x).
   - Dependencias: `drools-core`, `drools-compiler` y `drools-mvel`.
   - Dockerfile multi-stage con Maven para compilar y empaquetar el JAR, exponiendo el puerto 8080.

2. Modelos de Datos (`src/main/java/com/example/demo/model/`):
   - `DatosUsuario`: intencionPrincipal (String), cantidadSolicitada (Double), plazoMeses (Integer), proposito (String), gastosFijosMensuales (Double), deudaDeclarada (Double), dudaCatchAll (String).
   - `DatosCoreBancario`: clienteId (String), dni (String), edad (Integer), ingresosNetosMensuales (Double), antiguedadMeses (Integer), deudaInternaBancoMensual (Double), esAvalista (Boolean), empresaAvaladaCif (String).
   - `DatosExternosBde`: consultado (Boolean), tieneImpagosActivos (Boolean), importeMorosidadAsnef (Double), empresaAvaladaConcurso (Boolean), deudaCirbeMensual (Double), deudaCirbeTotal (Double).
   - `CalculosDerivados`: cuotaEstimada (Double), ratioEndeudamiento (Double), remanenteSubsistencia (Double), edadAlVencimiento (Integer).
   - `SolicitudEvaluacion`: Agrega instancias de DatosUsuario, DatosCoreBancario y DatosExternosBde.
   - `ResultadoEvaluacion`: 
     * estado (String inicializado en "EN_PROCESO")
     * reglasDisparadas (List<String> inicializada vacía)
     * accionRequerida (String)
     * datoFaltante (String)
     * articuloNormativo (String)
     * textoLegal (String)
     * tono (String)
     * calculosDerivados (CalculosDerivados)

3. Configuración y Controlador:
   - `DroolsConfig.java`: Configura `KieServices`, `KieFileSystem` cargando el DRL desde el classpath, `KieBuilder` y expone el `KieContainer` como Bean.
   - `RuleController.java`: Endpoint HTTP `POST /evaluar`. Recibe `SolicitudEvaluacion`, invoca `DroolsService` y devuelve `ResultadoEvaluacion`.

4. Servicio (`DroolsService.java`):
   - Inyecta el `KieContainer`.
   - Método `evaluar(SolicitudEvaluacion solicitud)`:
     1. Calcula matemáticamente los `CalculosDerivados` usando las fórmulas de SYSTEM_SPEC.md. Si alguna variable necesaria para el cálculo es `null`, el resultado de ese campo derivado debe ser `null` (previniendo `NullPointerException`).
     2. Instancia una `KieSession` stateless por petición.
     3. Inserta como facts en la sesión: `DatosUsuario`, `DatosCoreBancario`, `DatosExternosBde`, `CalculosDerivados` calculados, y un `ResultadoEvaluacion` recién instanciado.
     4. Ejecuta `kieSession.fireAllRules()`.
     5. Cierra la sesión (`dispose`), asocia los `CalculosDerivados` al `ResultadoEvaluacion` y lo retorna.

5. Reglas Drools (`src/main/resources/rules/prestamos.drl`):
   Implementa la sintaxis exacta de Drools para las 14 REGLAS. Cada regla debe evaluar `$res : ResultadoEvaluacion(estado == "EN_PROCESO")` y en el bloque `then` asignar: `$res.setEstado(...)`, `$res.getReglasDisparadas().add(...)`, `$res.setArticuloNormativo(...)`, `$res.setTextoLegal(...)` y `$res.setTono(...)`.

   Catálogo de reglas, salience y tonos:
   - R_EDAD_MINIMA (salience 100): `firme, claro y respetuoso`
   - R_CANTIDAD_Y_PLAZO_REQUERIDOS (salience 99): `amable, orientativo y conciso`
   - R_EDAD_MAXIMA (salience 98): `claro, respetuoso y transparente`
   - R_PROPOSITO_REQUERIDO (salience 97): `amable, cercano y orientativo`
   - R_PROPOSITO_NO_FINANCIABLE (salience 96): `firme, profesional y no acusatorio`
   - R_GASTOS_FIJOS_REQUERIDOS (salience 95): `amable, sencillo y orientativo (explicar que no se refiere a deudas, sino a gastos fijos como alquiler, recibos o suministros)`
   - R_DISPARAR_CIRBE (salience 70): `neutro y técnico` (accion_requerida: "CONSULTAR_CIRBE_ASNEF")
   - R_MOROSIDAD_ASNEF (salience 60): `firme, profesional y especialmente cuidadoso`
   - R_ALERTA_QUIEBRA_AVAL (salience 50): `serio, prudente y respetuoso`
   - R_DEUDA_DECLARADA_REQUERIDA (salience 45): `amable, claro y orientativo`
   - R_DISCREPANCIA_DECLARADA (salience 40): `neutral, prudente y no acusatorio`
   - R_RATIO_ENDEUDAMIENTO (salience 30): `firme, claro y respetuoso`
   - R_MINIMO_SUBSISTENCIA (salience 20): `serio, prudente y respetuoso`
   - R_APROBACION_ESTANDAR (salience 10): `positivo, claro y profesional`

6. Archivo KIE (`src/main/resources/META-INF/kmodule.xml`):
   Configuración canónica del módulo KIE.

Entrega el código íntegro de cada archivo, con imports completos, getters/setters y la implementación detallada del DRL sin elisiones ni comentarios de tipo TODO.













PROMPT FASE 2: Backend Orquestador (Python / FastAPI)


Actúa como un Desarrollador Backend Senior especialista en Python, FastAPI, SQLAlchemy y arquitecturas de integración de LLMs.
Tu objetivo es implementar el servicio `backend` según el archivo SYSTEM_SPEC.md, encargado de la orquestación, conexión con Mistral, gestión de base de datos MariaDB y registro de auditoría.

Requisitos técnicos del backend:
1. Framework: FastAPI con Uvicorn en el puerto 8000.
2. ORM: SQLAlchemy conectado a MariaDB (pymysql).
3. Cliente LLM: Uso de la librería oficial de Mistral (mistralai) para structured output garantizado mediante Pydantic.
4. Organización modular de carpetas según SYSTEM_SPEC.md:
   - config.py: Variables de entorno (DATABASE_URL, DROOLS_URL, MISTRAL_API_KEY).
   - database.py: declarative_base, create_engine, sessionmaker y generador `get_db()`.
   - models/:
     * cliente.py: Mapeo de la tabla 'clientes' (cliente_id, dni, edad, ingresos_netos_mensuales, antiguedad_meses, deuda_interna_banco, es_avalista, empresa_avalada_cif).
     * traza.py: Mapeo de 'trazas_auditoria':
       - id: BIGIN  AUTO_INCREMENT PK: Identificador único de la traza.
       - session_id: VARCHAR(64): Identificador único de la conversación del cliente.
       - turn_id: INT: Número de turno conversacional (1, 2, 3...). 
       - step_order: INT: Secuencia cronológica dentro del turno (1 a 6).
       - action_type: VARCHAR(64): Nombre formal: EXTRACT_NLU, FETCH_CORE_DATA, EVALUATE_PRELIMINARY, FETCH_CIRBE_ASNEF, EVALUATE_FINAL_DECISION, GENERATE_NATURAL_RESPONSE.
       - step_input JSON: Datos exactos entregados al componente.
       - step_output JSON: Respuesta devuelta por el componente.
       - information_state JSON: Snapshot consolidado del estado tras completarse el paso.
       - created_at TIMESTAMP: Marca de tiempo precisa para auditoría temporal.
   - schemas/:
     * nlu.py: Esquema Pydantic EsquemaNLU para la salida forzada de Mistral segun SYSTEM_SPEC.md.
     * drools.py: Modelos de intercambio con la API de Drools.
     * state.py: Modelo del Information State canónico segun SYSTEM_SPEC.md.
     * chat.py: Request (mensaje, cliente_id, session_id) y Response.
   - clients/:
     * mistral_client.py:
       - extraer_nlu(mensaje: str) -> EsquemaNLU: Prompt del sistema para estructuración en JSON con few-shot examples y structured output.
       - generar_nlg(state: dict, mensaje_usuario: str) -> str: Prompt estricto de solo lectura que usa el estado consolidado de Drools y su justificación normativa para generar el mensaje natural al usuario. Inyectar el tono devuelto también por drools. No generar nunca una explicacion legal si no viene en la respuesta de drools.
     * drools_client.py:
       - evaluar_reglas(payload: dict) -> dict: Llamada HTTP POST a DROOLS_URL con manejo de errores y timeout.
   - services/:
     * audit_tracker.py: Clase AuditTracker que recibe los datos necesarios para crear la fila atómica en la tabla trazas_auditoria.
     * bde_mock_service.py: Devuelve datos CIRBE/ASNEF simulados basados en el DNI del bde.json en raiz.
     * orchestrator.py: Contiene procesar_turno_conversacional(mensaje, cliente_id, session_id, db). Ejecuta los 6 pasos secuenciales definidos en SYSTEM_SPEC.md y registra cada micro-acción en el AuditTracker.
   - routers/:
     * chat_router.py: Endpoint POST /api/chat.
     * clientes_router.py: Endpoint GET /api/clientes (para alimentar la interfaz frontend con los usuarios posibles en el desplegable).
     * bde_mock_router.py: Endpoint GET /api/mock/bde/{dni}.
   - main.py: Inclusión de routers, CORS y montaje de estáticos en /static (que posteriormente se programarán).
   - requirements.txt: Lista de dependencias necesarias.
   - Dockerfile: Dockerfile funcional para compilar con pip.
   - bde.json: Archivo con datos simulados de CIRBE/ASNEF para el servicio bde_mock_service.py.
   - .env.example: Archivo con variables de entorno necesarias.
   - README.md: Archivo con instrucciones de uso detalladas, ve haciendolo conforme vayas programando para ir autocontextualizandote el proyecto y evitar así alucinaciones.
5. Paradigma de Programación Estricto (POO):
   - Todo el código debe estar estructurado mediante Programación Orientada a Objetos (clases y métodos).
   - Implementa clases de servicio bien definidas:
